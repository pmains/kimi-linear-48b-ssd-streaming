E3G correction record — 2026-09-01
===================================

The E3A/E3F "Metal compute ~2.8x the same-quantization CPU reference"
claim is INVALID. The CPU file E3A actually used was Q4_K_M, not MXFP4;
the true retained MXFP4 CPU references show compute parity with the
promoted MXFP4 Metal baseline. Details below.

1. What E3A/E3F actually compared
----------------------------------
E3A CPU reference file (per phase-11-e3a-report.md, used verbatim by
tools/phase11_e3a_analyze.py):
    benchmarks/results/phase-k1/full/coding-cap4/b8-A-after/stats.csv
Provenance of that run:
    manifest.json  -> "backend": "cpu", llama_commit caea707b7
    k1-model.json  -> model = moonshotai_Kimi-Linear-48B-A3B-Instruct-Q4_K_M.gguf
                       model_bytes = 30061058720  (30 GB Q4_K_M)
    run.log        -> "model : ...Q4_K_M.gguf", "ftype : Q4_K - Medium"
So the "same-quantization CPU reference" was CPU **Q4_K_M**, while the
Metal side was MXFP4 (E5 stats.csv, 360 decode steps). The comparison
was cross-quantization, and the "2.8x compute" figure (99.8 vs 36.0
ms/token) is invalid as a Metal-vs-CPU statement.

4. Conclusion
-------------
Metal MXFP4 route+expert compute (37.7 - 48.1 ms/token across controlled
arms; 43.82 at the promoted live point) is at PARITY with MXFP4 CPU
compute (35.4 - 68.5 ms/token; canonical 44.41), not 2.8x slower. The
E3A-era Metal number (99.8 ms/token) was measured on the E5 live server
at workers=1 under the pre-E3C read path and is not representative of
the controlled compute arms; and the CPU side of that comparison was the
wrong quantization anyway.

The E3G hypothesis (decompose a ~2.8x Metal-vs-CPU compute deficit) is
therefore FALSIFIED. Metal compute is parity work, not a backend deficit.
The 43.8 ms/token compute bucket in the E3F profile remains real Metal
wall time (48.3% of the 90.8 ms step) but is NOT a Metal-specific
inefficiency to hunt with an op-level Metal profiler.
